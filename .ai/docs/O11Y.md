# Observabilidade

Define o que registrar, onde e com que formato, para que um problema em produção possa ser entendido sem reproduzir localmente. Specs citam este arquivo ao definir eventos a logar.

## Ferramentas

| Sinal | Ferramenta | Onde consultar |
| ----- | ---------- | -------------- |
| Logs (backend) | Logs do Supabase Cloud (API, Postgres, Auth, Edge Functions) | Painel do Supabase › Logs (retenção de 1 dia no plano Free) |
| Métricas | Consultas SQL agendadas sobre as tabelas de negócio (sem ferramenta de métricas dedicada no MVP) | Supabase Studio › SQL salvo `metrics_*` |
| Traces | Performance do Sentry (amostragem 10% em produção) | Sentry › Performance |
| Erros (exceções) | Sentry (`@sentry/react-native`), com source maps enviados no EAS Build | Sentry › Issues |

## Logs

- Logs estruturados (JSON), nunca strings concatenadas. No app, nada de `console.log` em produção: erros vão para o Sentry, eventos de diagnóstico como breadcrumbs.
- Campos obrigatórios nas Edge Functions: `timestamp`, `level`, `event`, `request_id`; `user_id` (UUID) quando houver usuário.
- `event` em `snake_case`, no formato `<entidade>_<ação no passado>` (ex.: `event_published`, `push_dispatch_failed`).
- **Nunca** logar: tokens (JWT, push, OTP), chaves, e-mail, nome de pessoa, conteúdo de anotação, dados de chamado, corpo completo de requisições. No Sentry: `sendDefaultPii: false` e `beforeSend` removendo e-mail e qualquer campo de `notes`/`calling_processes`. Detalhes em `SECURITY.md`.

| Nível | Quando usar |
| ----- | ----------- |
| `error` | Falha que exige ação humana ou afetou a pessoa usuária |
| `warn` | Situação anormal tratada (retry, fallback, token de push inválido removido) |
| `info` | Eventos de negócio relevantes |
| `debug` | Diagnóstico local; desligado em produção |

Eventos de negócio previstos (`info`): `event_published`, `post_published`, `push_dispatched` (com contagem de destinatários, sem tokens), `account_deleted`, `data_exported`.

## Métricas

- **Adoção (métrica principal, `BUSINESS.md`):** eventos publicados por unidade por mês; % do calendário informado pelos secretários.
- Membros com push ativo por unidade; avisos por semana; reuniões com pauta registrada.
- Técnicas: taxa de sessões sem crash (Sentry, meta ≥ 99,5%); falhas de entrega de push por envio; latência p95 das Edge Functions.

## Alertas

| Alerta | Condição | Quem é avisado | Runbook |
| ------ | -------- | -------------- | ------- |
| Pico de crashes | Sessões sem crash < 99% em 24h, ou issue nova com > 20 eventos/h | Admin técnico (e-mail do Sentry) | A definir: `docs/runbooks/crash.md` |
| Falha no envio de push | `push_dispatch_failed` > 5% dos destinatários de um envio | Admin técnico | A definir: `docs/runbooks/push.md` |
| Backend fora do ar | Execução do `backup.yml` ou do `deploy.yml` falha (inclui projeto pausado) | Admin técnico (e-mail de falha do GitHub Actions) | `docs/runbooks/supabase-down.md` |
| Backup não executado | Execução do `backup.yml` falha | Admin técnico (e-mail de falha do GitHub Actions) | `docs/runbooks/backup.md` |

Sem monitor externo de uptime no MVP: o Supabase opera a disponibilidade (ADR 0004).

## Health checks

- `GET <SUPABASE_URL>/auth/v1/health` — GoTrue respondendo.
- `GET <SUPABASE_URL>/rest/v1/` com anon key — PostgREST e Postgres respondendo.
- Edge Function `health` (a criar) — verifica conexão ao banco e a configuração do Expo Push.
